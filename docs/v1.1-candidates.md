# v1.1 candidates

Everything this project has deliberately not built, collected in one place, sized, and ranked —
with a recommended scope at the end.

v1 is feature-complete: all six phases of [PLAN.md](./PLAN.md) are met. Nothing here is
outstanding work. These are choices.

## Where this came from

Nothing below is invented for this document. Each candidate already existed as a deferral, an open
question, or an ADR consequence, scattered across five files:

- **[PLAN.md](./PLAN.md)** — its "Deferred" section names the v1.1 trio and four later items
- **[SPEC.md](./SPEC.md)** — what v1 put out of scope, and why each was out
- **[HANDOFF.md](./HANDOFF.md)** — "Deliberately not built yet", and seven open questions
- **[docs/adr/0002](./adr/0002-regular-proxy-mode-for-v1.md)** — defers `--mode local`, and explains
  what regular proxy mode costs
- **[docs/adr/0005](./adr/0005-pull-based-live-access.md)** — defers push, as an enhancement that
  would not change the existing tools

Three candidates are **new here** and marked as such. They follow from reading the v1 code rather
than from a prior deferral, and each is noted with what in the code makes it a gap.

Vocabulary is [CONTEXT.md](../CONTEXT.md)'s, used precisely.

## Permanently out of scope

Not candidates, and worth restating so nobody proposes them:

- **Production traffic monitoring.** SPEC.md says *never*, not *later*. This is a debugging tool
  pointed at an app under test on a developer's machine.
- **Correctly-pinned release builds.** `diagnose_capture` reports pinning as pinning rather than
  pretending to defeat it. Defeating it is out.

## Recommended v1.1

If v1.1 should be one coherent release rather than a grab bag:

**Ship #7, #8, #9 first, in a week or less.** All three are small, all three are pure additions, and
they exercise the release process on low stakes before anything risky lands. #7 in particular is a
genuine hole in the current surface for very little work.

**Then #2, write and interception tools.** Medium cost, contained risk, behind
`--enable-write-tools` as PLAN.md already specifies. It is the largest capability gap that does not
depend on an unverified platform behaviour, and it needs no new Capture Target.

**Run #3 as a timeboxed probe alongside, not as a feature.** One day to answer open question 1 —
can `--mode local:<spec>` scope to a process inside CoreSimulator? The answer changes what #1 and
`diagnose_capture` can promise. Probing before designing is this project's own method and it has
paid every time.

**Hold #1, Android, for v1.2 unless it is the actual reason for v1.1.** Not because the
architecture is not ready — it is, and that is the point of the adapter contracts — but because
SPEC.md's own assessment stands: its system-CA procedure is *"the most brittle part of the domain"*.
It deserves a release of its own rather than sharing one.

**#4, #5, #6 are all defensible and none is urgent.** #4 is the most valuable of the three because
it removes a documented dead end rather than adding surface.

## 1. Android Emulator Capture Target

**What.** A second `CaptureTarget`: route an emulator's egress through the proxy, install the
Interception Authority where an arbitrary app will trust it, and diagnose the five failure modes.

**Why.** The single largest capability gap. Everything else on this list makes the iOS story better.

**Known.** The architecture was built for exactly this and the claim is now testable rather than
aspirational: `targets/base.py`'s protocol is all the core depends on, and
`tests/test_targets.py` ends in a suite parametrised over every registered target, asserting only
what that protocol promises. A third target inherits the contract by being registered — including
the promise a newcomer is most likely to break by omission, that `trust_status` changes nothing.

**Unknown, and this is the whole risk.** SPEC.md kept Android out of v1 on the grounds that its
system-CA procedure is *"the most brittle part of the domain and must not gate the first release"*.
That judgement has not been revisited. Specifically unverified:

- Since API 24 an app does not trust user-installed authorities unless its
  `network_security_config` opts in, so capturing an arbitrary app needs the **system** store —
  which means `emulator -writable-system` plus `adb remount`, or Magisk on a rooted device. PLAN.md
  records the certificate filename convention as `<subject_hash_old>.0`. **All of this is inherited
  from the research that preceded the project and none of it has been probed.**
- Whether routing is `emulator -http-proxy` at boot, `adb shell settings put global http_proxy`
  at runtime, or per-API-level both.
- Whether trust is *observable* after installing, the way iOS trust turned out to be readable from
  `TrustStore.sqlite3`. `get_trust_status` exists because verifying beats inferring, and a target
  that cannot verify weakens that guarantee.

**Cost.** High. Comparable to P3, which was a whole phase.

**Do this first.** Probe each unknown with a throwaway script against a throwaway emulator before
designing anything. P3's entire design came out of four such probes and two of them contradicted the
documentation; P4's changed its design twice. Budget for the probes to change the plan.

**Acceptance.** Capturing a real emulator app's HTTPS traffic end to end, on a throwaway emulator,
with the shared contract suite passing unmodified — and the machine's state byte-identical
afterwards.

## 2. Write and interception tools

**What.** Modify traffic in flight: rewrite a request or response, inject a status code, delay,
fail a connection. Behind `--enable-write-tools`, per PLAN.md.

**Why.** SPEC.md lists "no write/interception tools in v1" as a deliberate deviation from **all**
surveyed prior art. Reading traffic answers *why did this fail*; writing it answers *what happens
if the token expires mid-session* — which is a test an agent cannot otherwise write.

**Known.** mitmproxy supports it natively and the addon is already the only module that touches
mitmproxy's own object shapes, so the blast radius is contained to `capture/addon.py` and a new
tool group. The flag is already named.

**Unknown.** The safety design, which is the real work rather than the plumbing:

- A rule has to be *scoped* and *expiring*, or a forgotten rewrite silently poisons every later
  Run. This is the same class of hazard as the system proxy, and the sentinel protocol is the
  precedent for how seriously it gets treated.
- Whether rules belong to a Session or a Run.
- How a Timeline shows that an Exchange was **modified**. An Exchange that was tampered with and
  reads as genuine is the worst outcome available here — worse than not having the feature.

**Cost.** Medium.

**Acceptance.** An agent makes `GET /me` return 401 for one host, drives the app, and the Timeline
shows both the injected response *and* that it was injected — then the rule expires and the next Run
is unaffected.

## 3. `--mode local` — a probe, not a feature

**What.** mitmproxy's transparent per-process capture, as an opt-in iOS path alongside the system
proxy. [ADR-0002](./adr/0002-regular-proxy-mode-for-v1.md) deferred it; open question 1 is whether
it can work at all here.

**Why it is more interesting than it looks.** Regular proxy mode has **no process attribution** —
every connection arrives from localhost, so simulator traffic and browser traffic are
indistinguishable. That single consequence is why:

- `diagnose_capture` will not report `tls_failed` without a Scope. With process attribution it
  could report pinning unconditionally, and SPEC.md calls `diagnose_capture` the highest-value tool
  in the set.
- Host filtering is *"not a convenience here, it is the only available mechanism"*.
- Capturing at all means proxying the entire Mac, which is why teardown is safety-critical.

Process attribution would relax all three — but **less than it did when this was written**, and the
change is worth reading before spending the day. [ADR-0007](./adr/0007-passthrough-scoped-interception.md)
made a Scope narrow what is decrypted, so host filtering is no longer only a *reporting* mechanism
and the collateral damage it existed to work around is largely gone: with a Scope, an out-of-scope
HTTPS connection is passed through untouched, the developer's browser and every other simulator are
unaffected, and no other application's handshakes fail against the proxy. Verified by hand, by
issuer, on a real capture.

So what a probe would still buy is narrower and should be stated as such:

- **Pinning without a Scope.** Unchanged and still the biggest prize. Passthrough needs a Scope to
  do anything, so an unscoped Session is exactly as noisy as it always was.
- **Plain HTTP.** Passthrough covers TLS only, because the engine picks a layer before a plain-HTTP
  request names its destination. Process attribution would cover it.
- **The availability blast radius.** Out-of-scope connections are still *forwarded by* this process,
  so the machine's traffic still stops if it dies. Passthrough shrinks the certificate blast radius
  and not this one.

The **certificate** blast radius, which was the loudest of the three, is already addressed.

**Unknown, and it is one question.** Can `--mode local:<spec>` scope to the app process running
inside CoreSimulator? ADR-0002's stated fear is paying the cost of a code-signed macOS Network
Extension — which normally needs user approval in System Settings — and **still** capturing the whole
host.

**Cost.** A day to probe. High and uncertain to build, and ADR-0002 already rejected carrying two
capture paths with a fallback matrix in the riskiest component.

**Recommendation.** Answer the question, write the answer into ADR-0002 as an amendment, and decide
afterwards. A negative answer is worth as much as a positive one: it closes open question 1
permanently and settles that `tls_failed` stays scope-dependent.

## 4. Background `run_test`

**What.** Let `run_test` return immediately and report progress, instead of blocking until the test
command exits.

**Why.** This is open question 6, and it is the only place the tool surface has a documented dead
end. Because `run_test` blocks, explicit Steps cannot be interleaved with it — so `start_step` and
Maestro's artifacts cover their cases separately and nothing is unreachable, but a caller who wants
*both* is stuck. `get_timeline` returns an explanatory `note` when this bites, which is a good
consolation prize rather than a fix. It would also make `tail_exchanges` and `wait_for_exchanges`
usable *during* a Run, which is what they were built for.

**Known.** The Run window is process lifetime and does not change. `RunRegistry.complete` already
separates creation from completion, so a Run that is still open is a shape the registry has.

**Unknown.** How a caller learns the Run finished, given pull-only access
([ADR-0005](./adr/0005-pull-based-live-access.md)) — presumably a `wait_for_run`, which is
`wait_for_exchanges`' shape and therefore no new mechanism. And what `get_timeline` does for a Run
still in progress, where `window` has no end. If implementing this adds a fourth consumer of the
`run_or_session` + `_steps_for` + `_traffic` triple, evaluate a `RunView` (resolve + steps +
narrowed traffic, assembled once) before hand-assembling it a fourth time — deferred from the
2026-09 architecture review with exactly this as its reopening trigger.

**Cost.** Medium. Touches the Run lifecycle, which every Timeline depends on.

**Acceptance.** Start a Maestro Run in the background, mark explicit Steps while it runs, and get
one Timeline containing Steps from both Event Sources.

## 5. More Event Sources: Detox, Appium, Playwright, XCUITest

**What.** Artifact parsers for other test tools, alongside `MaestroEventSource`.

**Why.** Open question 3. Less pressing than it once was, and worth being honest about why:
`start_step` / `end_step` already covers any of these with no adapter at all. So this is
**enrichment**, not reach — it removes the need to instrument a test by hand.

**Known.** `Step` is `{t_start, duration_ms, label, status, error?}` and nothing in it is
Maestro-shaped. `tests/test_eventsources.py` ends in a suite parametrised over every Event Source.
Both facts mean an addition, not a refactor.

**Unknown.** Open question 3's actual question: do these tools expose per-Step timings rich enough
for the contract? Maestro's `commands-*.json` did, but only after a probe found it was **not in
execution order** — a trap that every test would have passed through silently. Assume each new tool
hides one of those.

**Cost.** Medium, and it divides cleanly: one parser at a time, each independently shippable.

**Acceptance.** Per tool: a real failing run through `run_test` produces a Timeline whose Steps came
from the artifacts, with no explicit marks.

## 6. WebSocket message capture

**What.** Record individual WebSocket frames, not just the upgrade.

**Why.** Today the upgrade Exchange **is** captured and classed long-lived — status `101` or
`text/event-stream`, owned once by the Step that opened it and never repeated as an Overlap, which
is P4's answer to open question 2. What is missing is the contents. For an app whose real traffic is
a socket, the Timeline currently says a socket opened and nothing about what went over it.

**Known.** `capture/addon.py` implements `request`, `response`, `error` and `tls_failed_client` —
**no `websocket_message` hook**, so this is genuinely unbuilt rather than half-built. The pinned
mitmproxy dispatches three relevant hooks (`websocket_start`, `websocket_message`, `websocket_end`),
verified by introspecting the installed package rather than the docs.

**Unknown, and it is a modelling question rather than a plumbing one.** A frame is not a
request-plus-response, so it is not an Exchange (CONTEXT.md). Is it a third record type beside
Exchange and PendingExchange? How does a Timeline show a thousand frames without flooding the
context the whole API shape exists to protect? Answering that is most of the work.

**Cost.** Medium, dominated by the modelling.

**Acceptance.** A real WebSocket conversation is readable frame by frame through a paged tool, and a
Timeline over it stays summary-first.

## 7. A tool that lists open requests *(new)*

**What.** A read-only tool for the pending registry — the requests recorded as started with no
response yet.

**Why.** *"What is the app waiting on right now?"* is one of the most natural questions to ask this
server, and today there is no direct way to ask it. A request that never came back is invisible to
`list_exchanges` by construction, because the store records on **completion**.

**What makes it a gap.** The data already exists and is deliberately durable — `ExchangeStore` keeps
a pending registry that survives `close()`, precisely because "two requests were still open when
the Session ended" is often the answer. But it reaches a caller in only two places:
`serialize/timeline_views.py`, so `get_timeline` shows it inside a Run's window; and
`server/state.py`, where `get_status` reports a bare **count**. So an agent that has not run a test
can learn that three requests are open and nothing whatever about them.

**Known.** Everything. The registry is there, capped at 500, and the Timeline already has a view
shape for an open request — a summary with a **null id**, since ids are assigned on completion.

**Unknown.** Almost nothing. Whether it takes a filter, and whether it is exempt from the denylist
and Scope like `wait_for_exchanges` and `get_exchange` are. Probably yes, for the same reason: it is
an explicit question.

**Cost.** Low — a tool, a view, tests, and one line in `REGISTERED_TOOLS`, `SKILL.md` and
`docs/USAGE.md`. Note that adding a tool is deliberately three edits, and the surface is asserted
exactly.

**Acceptance.** With a request outstanding against a server that never answers, the tool names the
host and path and says how long it has been open — with no Run in the Session.

## 8. Reading Runs and Sessions back from disk

**What.** Let `list_runs` and `get_timeline` see a Session that this process did not create.

**Why.** Post-hoc diagnosis: *"the nightly run failed, tell me why"* against a Session directory
that already exists. Sessions are retained ten deep, so the material is normally still there.

**What makes it a gap.** `runs/registry.py` writes `run.json` for durability and keeps its index
**in memory only** — its methods are `create`, `complete`, `get`, `all`, `latest` and `_write`, with
no read path at all. So a Session found later is readable by hand and not by any tool. Likewise
`exchanges.ndjson` is an append log with a documented round-trip, and nothing loads it back.

**Known, stated precisely because it affects the estimate.** One *record* already round-trips:
`Exchange.from_log_dict` and `BodyRef.from_log_dict` exist alongside their `to_log_dict` halves. What
does not exist anywhere in `capture/` is a **file** reader — no call site parses `exchanges.ndjson`
back. `Run` has only the write half, `to_manifest`, with no inverse. So the work is a loader and a
`from_manifest`, on top of per-record plumbing that is done and tested.

Session ids are microsecond timestamps, so lexicographic order is chronological and *listing*
Sessions needs no file opened at all — which is also why retention already prunes correctly even
when a manifest is corrupt.

**Unknown.** Whether reopening is read-only or resumes recording — read-only is obviously right, and
worth stating so nobody builds resume. And what happens to bodies pruned by retention while their
metadata survives.

**Cost.** Low. Mostly the inverse of code that exists.

**Acceptance.** Point the server at a Session directory from a previous process and get the same
Timeline that process would have produced.

## 9. `json_path` on `get_exchange_body`

**What.** Extract one path out of a JSON body instead of slicing bytes.

**Why.** It is in **SPEC.md's own tool table** and was never implemented — one of four places that
table has drifted from the code. And it fits the central design idea better than slicing does: the
point of progressive disclosure is to fetch the part you need, and `offset`/`length` is a poor
approximation of that for structured data.

**Known.** The parameter's name and position are already specified.

**Unknown.** Only the decision HANDOFF.md records: a JSONPath dependency, or a hand-rolled subset.
Given `search_exchanges` deliberately exposes mitmproxy's existing filter language rather than
inventing one, the consistent choice is a real dependency rather than a homegrown dialect.

**One trap.** Redaction runs **before** truncation and slicing, deliberately, so a path must be
evaluated against the **redacted** body — or `json_path` becomes the one route by which a secret
leaves unredacted.

**Cost.** Low.

**Acceptance.** `json_path="$.user.id"` returns the value; a path into a redacted subtree returns the
redaction marker, not the secret; and a test asserts the second one.

## 10. Housekeeping

Small, unglamorous, cheap.

- **A version policy.** Open question 7. `serverInfo.version` now reports ours rather than the
  SDK's, so the number means something to a client for the first time — and nothing bumps it.
  Decide what it tracks before there is a second release.
- **`simplify` on `server/run_tools.py` and `serialize/timeline_views.py`.** Named as an optional
  P5 quality pass and not taken. Nothing about either is known to be wrong.
- ~~**`ruff format` across the tree.**~~ **Done**, in one deliberate commit of nothing else, as
  this entry asked. `ruff format --check` is now a gate in pre-commit and in CI, so the tree
  cannot drift back.
- **Verify binary body handling against real traffic.** Open question 5: non-UTF-8 bodies are
  described in previews and base64'd in slices, which is settled but has **never been used against
  real binary traffic**. An hour with an image endpoint either confirms it or does not.
- **Publication.** Built and locally verified under every supported interpreter; not uploaded, by
  choice. If it ever happens, TestPyPI first — the local suite cannot tell you a long description
  failed to render.
- **A reverse check on `SKILL.md`.** A test asserts every registered tool is named there; the other
  direction is not asserted, because telling a tool name from a parameter name in prose needs a
  curated exclusion list. Revisit only if the skill ever names a tool that does not exist.
- ~~**Give the three gated live machine tests a `scope`.**~~ **Done, all three.**
  `test_simulator_e2e.py`'s two carry `scope=["example.com"]`. `test_maestro_e2e.py` carries
  `["example.com", "192.0.2.1"]` and arranges its own in-flight request rather than relying on
  Safari's chatter — see the next entry, which was the blocker. A run now logs **zero** client
  handshake failures where it used to break `www.figma.com`, `discord.com`, `as.atlassian.com`,
  `us.i.posthog.com` and `api.copilot.mobile.dev`, Maestro's own endpoint.
- ~~**A deterministic in-flight Exchange for `test_maestro_e2e.py`.**~~ **Done**, and the route to
  it is worth keeping because two of the three obvious approaches are dead ends. The flow now opens
  `http://192.0.2.1/never-answers` before its failing assertion: an RFC 5737 documentation address,
  reserved and unroutable, so the request is registered as pending the moment mitmproxy parses the
  request line and stays that way through the assertion. The dead ends: a Scope alone leaves the
  assertion with nothing in flight, and a hanging listener on the host's own LAN address is fetched
  by the device but **bypasses the proxy entirely**, which is what the older "openLink does not
  fetch a private-IP URL" note had mis-attributed. The one environmental assumption is that the
  network drops that range rather than rejecting it; if it rejects, the request completes at once
  and the test says so.
- ~~**TLS failures are counted per machine, not per client.**~~ **Fixed 2026-08-18**, and the route
  matters more than the fix. This was filed as a candidate on the strength of an incidental
  observation; it was then reproduced deliberately as a negative control — one Session, two legs,
  nothing about the device changed — and the deliberate reproduction is what showed it had already
  produced a **false conclusion in this repository's own documents**: the app under test was
  recorded as certificate-pinned on this verdict's word, and it is not. Leg A: the real app on a
  trusting device, `ok`, `tls_failures: 0`. Leg B: one request from an unrelated process on the same
  Mac to the same in-scope host, and the verdict flipped and named that device.

  The counter still cannot tell which client failed and **no version of it can**: every client
  reaches the proxy over loopback, so there is no peer address to separate a simulator from a
  browser. Only the wording was fixable. The verdict now states the count is machine-wide and offers
  pinning as the leading candidate beside the cheaper cause; three tests go red if either claim
  returns. The generalisable lesson is the one in `HANDOFF.md`: a diagnosis that names a specific
  actor is read as evidence about that actor, so a diagnosis that cannot identify one must say so in
  the sentence itself, not in a caveat elsewhere.
- **`test_runtime.py::test_stopping_releases_the_port` flaked once, cause unknown.** *(new.)*
  It failed in one full `uv run pytest -q` — `accepts(port)` answered `True` after `stop()` —
  and then passed in the next two full runs, in ten consecutive standalone runs, and in isolation
  immediately afterwards. Nothing was changed in between; the tree at the time carried only test
  edits, in three files `test_runtime.py` does not import. Recorded rather than explained away,
  because the guarantee it covers is a real one: a listener that outlives `stop()` makes the next
  `start_capture` on that port fail. No mechanism is claimed here — `stop()` clears the mode,
  shuts the master down and awaits its task under a 15 s timeout, and a 15 s stall inside a 48 s
  suite is not credible, so the timeout branch is not it. If it recurs, capture
  `lsof -nP -iTCP:<port>` at the moment of the failure before doing anything else.
- **`CurlTarget.diagnose` does not know about Passthrough.** *(new.)* It always answers `ok` with
  "if no Exchanges are appearing, check that curl was given `-x http://127.0.0.1:<port>`". A `curl`
  Session with a `scope` has Passthrough on by default, so an out-of-scope HTTPS host was never
  decrypted and that advice is incomplete in exactly the way ADR-0007 exists to explain.
  `observed.passthrough` is still reported, so the premise is visible rather than hidden, and the
  curl target never returns `no_connect` or `out_of_scope` — which are the two verdicts the caveat
  attaches to. So user story 9 is satisfied for the iOS target and not for `curl`. Low cost: append
  the same caveat, and give it a test.
- **Nothing warns that a *second* device already trusts the Authority.** *(new, 2026-08-18.)* This
  is the machine-wide finding above arriving from the other direction, and it is the likelier way
  to get hurt by it, because it produces plausible data instead of an obvious failure.

  Measured on this machine, with `get_trust_status` and nothing running: `iPhone 17 Pro - Main`
  **trusts** the Authority at `~/.https-proxy-mcp/mitmproxy/`, and `Sidekick` does not. Neither is
  a surprise — `ensure_authority` never regenerates, so the default root's Authority is stable
  across every Session ever run here, and `install_authority` persists in a device's trust store
  until `simctl erase`. Trust granted to a device months ago is still in force today, and nothing
  in the tool ever mentions it again.

  The consequence, for the workflow the tool is *for* — an agent running an autonomous capture on
  one simulator while a human drives the app on another: the human's in-scope HTTPS is **decrypted
  and recorded** into the agent's Session. Not rejected, not counted as a failure — recorded, as
  ordinary Exchanges. There is no separating them: every client is loopback and regular proxy mode
  has no process attribution (ADR-0002), and both devices run the same app so no host filter helps.
  Ownership is gap-tolerant by design (ADR-0004), so a request the human fires while a Step is open
  is owned by *that Step* and rendered as the thing it caused. `wait_for_exchanges` is exempt from
  the Scope and counts anything recorded after the call, so the human's login can satisfy the
  agent's wait. The agent is then diagnosing from traffic the agent did not cause, and the Timeline
  says so in its primary sentence.

  Worth stating because it is not a bug and cannot be fixed by narrowing anything: **on shared
  hosts you cannot have both.** A device must trust the Authority for its app to work through a
  machine-wide proxy at all, and trusting it is exactly what puts its traffic in the Session. The
  one clean case is a manual device talking to hosts the Scope does not name, where Passthrough
  tunnels it unopened.

  Cheap remedy, and it is diagnosis rather than enforcement — nothing here should refuse to start:
  at `start_capture`, and in `diagnose_capture`'s `observed`, name the **other booted simulators
  that also trust the Authority**. Both halves are already implemented — `simctl list devices -j`
  for the booted set, `get_trust_status`'s trust-store read for each — so this is a listing and a
  sentence, not a mechanism. The sentence is the deliverable: *"2 other booted devices trust this
  Authority; traffic they send to an in-scope host is recorded here and cannot be told apart from
  the capture target's."* Give it a test with two devices in the fake `simctl` table, one trusting
  and one not.

## 11. Attributing an Exchange to a device *(new)*

**What.** Record which device a request came from, so a listing can be narrowed by client without
the client having to say so.

**Why it is not v1.** ADR-0009 solved the problem this addresses — two simulators on one Mac
sending the same traffic to the same hosts — with the **Lens**, which takes the client's own word
for it via a header the debug build stamps. That is exact, free at the proxy, and needed no new
machinery. This candidate is the version that works when the app cannot be changed.

**It is feasible, and the chain was traced rather than assumed.** `flow.client_conn.peername` gives
the connecting socket's ephemeral port on loopback. `lsof -nP -iTCP:<port>` maps that to a pid.
Walking the PPID chain reaches a `launchd_sim`, and each booted device has exactly one, carrying its
UDID in its own command line:

```
1662  launchd_sim .../CoreSimulator/Devices/2523F6C8-…-1C13C9C9931F/data/var/run/…
59922 launchd_sim .../CoreSimulator/Devices/F48AAE9F-…-7B4B0024CF07/data/var/run/…
93050 launchd_sim .../CoreSimulator/Devices/DD9BE74D-…-F6478CADF4A9/data/var/run/…
```

Measured on a Mac with three booted simulators. Traffic from a per-device daemon rather than the app
process still resolves correctly, because each device's daemons live under its own `launchd_sim`.

**And the query language is already waiting for it.** `mitmproxy.flowfilter` ships `FSrc`/`FDst` —
`~src` and `~dst`. The gap is purely in the data model: `filtering.py`'s `as_flow` hardcodes
`peername=("127.0.0.1", 0)` because an `Exchange` records `server_address` and no client address at
all. Adding one would light up `~src` for free.

**Cost, honestly.** An `lsof` per new client connection, plus a PPID walk; caching per client port,
since connections are reused. A race — the socket must still be open when it is resolved, so it
happens at connection time and not at reporting time. A new field in `to_log_dict`, which is written
out by hand precisely so an addition is never silent. And a naming problem: `CONTEXT.md` defines a
**Capture Target** as singular per Session and lists *device* as a word to avoid, so traffic
originating from something that is not this Session's Capture Target has no term yet. Settle the
word before writing the field.

**What it would additionally buy.** `diagnose_capture` could stop hedging on `tls_failed`. That
verdict's count is machine-wide because loopback leaves nothing to attribute it to; a resolved
client address is exactly what it lacks. Note this is a *different* problem from the Lens's, and
the Lens cannot help with it — a handshake failure never becomes an Exchange, so no predicate over
Exchanges can narrow it.

## Deferred beyond v1.1

PLAN.md's "Later", unchanged and listed for completeness:

- **Physical devices**, via mitmproxy's WireGuard mode.
- **Browser Capture Targets.** Cheaper than they look — `install_authority_system` already exists
  for exactly this — but a browser has no Event Source, so a Timeline over one has Background and
  nothing else until explicit Steps are marked by hand.
- **MCP notification-based push**, if client support becomes dependable. ADR-0005 is explicit that
  this would be an *enhancement* and would not change `tail_exchanges` or `wait_for_exchanges`, so
  it costs nothing to keep waiting.
- ~~**`mitmweb` for a human view.** Already free: it drives its UI from the proxy core, so pointing
  it at the same capture costs this project nothing to support.~~ **Done**, as the **Human View**:
  `start_capture(web_ui=True)` serves the mitmweb UI from the Session's own proxy core, live and
  token-gated (ADR-0010). The struck premise was never true, and the correction is why it took a
  feature rather than a sentence: a separate `mitmweb` binary could never attach to this capture,
  because the proxy is an in-process master and a second process would be its own empty core. What
  it took was the constructor swap inside this one.

## Questions this document does not answer

- Which of these anyone actually wants. The ranking above is on capability gap and risk, not on
  demand, because there is no usage data.
- Whether v1.1 should be one release or three. The recommendation assumes three small ones are
  safer than one large one, which is a preference rather than a finding.
- Whether Android or write tools is the better headline. Both are defensible; Android is the bigger
  capability and the bigger risk.
